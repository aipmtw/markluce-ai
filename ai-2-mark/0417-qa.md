## 1. SECURITY CONCERNS

### S-01. LINE Channel Secret hardcoded in source code — CRITICAL

**File:** `api/line-auth.js`, lines 1–2
```js
const LINE_CHANNEL_ID = '2009738746';
const LINE_CHANNEL_SECRET = '030f5af9d09f93db8983cd76b6200df8';
```

The LINE Login channel secret is hardcoded in server-side code that is committed to git. If this repo is public (it links to `github.com/aipmtw/markluce-ai`), the secret is fully exposed. An attacker can forge LINE Login tokens or impersonate users.

**Fix:** Move to environment variables. Rotate the secret immediately if the repo has ever been public.

---

### S-02. Database password hardcoded in scripts (committed to git) — CRITICAL

**Files:**
- `scripts/seed-24-books.js`, line 5: `password: '02uL6rlxF2feKlY8'`
- `scripts/seed-paid-books.js`, line 5: same password
- `scripts/post-brief-20260415.js`, line 8: same password

The Supabase Postgres password is hardcoded in three script files. These are not in `.gitignore`.

**Fix:** Use `process.env.SUPABASE_DB_PASS` and add scripts with credentials to `.gitignore`, or use `.env` loading. Rotate the database password.

### S-03. `.env` file tracked in git staging — CRITICAL

**File:** `.env` (status shows `M .gitignore` and `.env` exists with secrets)

The `.env` file contains:
- `SUPABASE_SERVICE_KEY` (service role key — full database admin access)
- `SUPABASE_DB_HOST`
- `SUPABASE_DB_PASS`

While `.env` is listed in `.gitignore`, git status shows `.gitignore` itself was modified (`M .gitignore`), suggesting `.env` may have been tracked at some point. If it was ever committed, the secrets are in git history.

**Fix:** Verify `.env` was never committed with `git log --all -- .env`. If it was, rotate all credentials and use `git filter-branch` or BFG to purge history.

### S-04. Supabase ANON_KEY hardcoded in server-side API files — HIGH

**Files:** `api/book-pages.js:2`, `api/books.js:2`, `api/inquiry.js:2`, `api/track.js:5`, `api/brief.js:2`, `api/briefs.js:2`, `api/features.js:2`, `api/mvp-get.js:2`, `api/partner-apply.js:2`, `api/site-config.js:2`

The same Supabase anon key (`eyJhbG...EfSo`) is copy-pasted across 10+ API files. While anon keys are designed to be public, having them in server-side code means:
1. If you ever need to rotate, you must update 10+ files
2. The key is also in client-side HTML files (see S-05), creating inconsistency risk

**Fix:** Centralize into a shared config module or environment variable.

This is acceptable IF Row-Level Security (RLS) policies are properly configured on all tables. Verify RLS is enabled on all tables in both Supabase projects.

### S-06. Hardcoded admin password with weak default — CRITICAL

**Files:** `api/admin.js:2`, `api/sql.js:8`, `api/book-logins.js:5`, `api/brief.js:24`, `api/site-config.js:27`

```js
const ADMIN_PASS = process.env.ADMIN_PASS || 'aipm2026';
```

The fallback admin password `aipm2026` is hardcoded in 5 API endpoints. If `ADMIN_PASS` env var is not set in production, anyone who reads this source code can access:
- ESL analytics data
- Raw SQL execution
- Book login data with user PII (names, IPs, user agents)
- Site config modification
- Brief creation

**Fix:** Remove the fallback. Fail closed if `ADMIN_PASS` is not set (return 500).

---

### S-07. SQL injection via raw SQL execution endpoint — CRITICAL

**File:** `api/sql.js`

This endpoint accepts arbitrary SQL queries and executes them against the production database. Even though it requires `ADMIN_PASS`, the password is weak (see S-06) and passed in query strings/headers (not session-based auth). An attacker who discovers the password can DROP tables, exfiltrate all data, or escalate privileges.

**Fix:** Remove this endpoint from production entirely, or at minimum:
- Require strong auth (not a static password)
- Whitelist allowed query patterns
- Use a read-only database role

---

### S-08. Admin password sent in URL query string — HIGH

**File:** `public/admin/index.html:226`, `public/admin/index.html:283`, `public/esl/admin.html`

```js
fetch('/api/book-logins?pass=' + encodeURIComponent(adminPass) + '&days=' + days);
fetch('/api/admin?pass=' + encodeURIComponent(adminPass) + '&days=' + days);
```

The admin password is sent as a URL query parameter. Query strings are logged in server access logs, browser history, proxy logs, and Vercel function logs. This leaks the password.

**Fix:** Send the password only via the `x-admin-pass` header (which some endpoints already support).

---

### S-09. Cookie secret has a weak hardcoded default — HIGH

**Files:** `api/line-auth.js:8`, `api/book-key.js:2`, `api/ecpay-create.js:11`, `api/user-books.js:4`

```js
const COOKIE_SECRET = process.env.LINE_COOKIE_SECRET || 'markluce-line-2026';
```

The HMAC signing key for auth tokens defaults to `markluce-line-2026`. If `LINE_COOKIE_SECRET` is not set, any attacker who reads the source code can forge auth tokens for any user.

**Fix:** Remove the fallback. Fail if the env var is not set.

---

### S-10. ECPay staging credentials hardcoded — HIGH

**Files:** `api/ecpay-callback.js:3-11`, `api/ecpay-create.js:4-7`

ECPay merchant ID, hash key, hash IV, and invoice credentials are all hardcoded as defaults:
- `MERCHANT_ID: '3002607'`
- `HASH_KEY: 'pwFHCqoQZGmho4w6'`
- `HASH_IV: 'EkRm7iFT261dpevs'`
- Invoice: `INV_MERCHANT_ID: '2000132'`, `INV_HASH_KEY`, `INV_HASH_IV`

These are staging credentials but still should not be in source. If accidentally used in production, payment data is at risk.

**Fix:** Move all to env vars with no defaults. Fail if not set.

### S-11. Auth token passed via URL query parameter on redirect — HIGH

**File:** `api/line-auth.js:107-109`

```js
url.searchParams.set('ml_token', token);
url.searchParams.set('ml_user', profile.displayName);
return res.redirect(302, url.toString());
```

When `returnUrl` is an external URL, the full signed auth token is appended as a query parameter. This token is logged in browser history, server logs, and any analytics tools on the destination page. The token is valid for 90 days.

**Fix:** Use a short-lived exchange code pattern instead of passing the long-lived token directly.

---

### S-12. CORS set to wildcard `*` on sensitive endpoints — HIGH

**Files:** `api/book-key.js:18`, `api/user-books.js:19`, `api/ecpay-create.js:60`

These endpoints handle authentication (book-key returns decryption keys, user-books returns user data, ecpay-create initiates payments) but use `Access-Control-Allow-Origin: *`. This allows any website to make authenticated requests if cookies are sent.

**Fix:** Restrict to `https://markluce.ai` and `https://app.markluce.ai`.

---

### S-13. XSS risk: unsanitized data inserted via innerHTML — MEDIUM

**File:** `public/admin/index.html:233-244`

User data from the API (display names, picture URLs, IPs) is inserted via string concatenation into `innerHTML` without escaping. If a LINE user has a malicious display name like `<img src=x onerror=alert(1)>`, it will execute in the admin's browser.

Also in `public/admin/index.html:270-275` — feature slugs/titles inserted via template literals into innerHTML.

**Fix:** Use `textContent` for text data, or escape HTML entities before insertion.

---

### S-14. `verifyToken` does not use timing-safe comparison — MEDIUM

**Files:** `api/book-key.js:10`, `api/ecpay-create.js:19`, `api/user-books.js:11`

```js
if (sig !== expected) return null;
```

The HMAC signature comparison uses `!==` (string comparison), which is vulnerable to timing attacks. An attacker could theoretically determine the correct signature byte-by-byte.

**Fix:** Use `crypto.timingSafeEqual()`.

---

### S-15. Admin LINE ID hardcoded in client-side HTML — MEDIUM

**File:** `public/admin.html:356`

```js
var ADMIN_LINE_ID = 'U7d41d4b9a49052370bd3a7265c1e391b';
```

The admin check is done client-side by comparing the logged-in LINE user ID. This means:
1. The admin's LINE user ID is exposed publicly
2. The check is trivially bypassable (modify JS in browser)

The admin.html page loads data from the classmates Supabase project using the publishable key, so the actual data access is gated by RLS on that project, not by this client-side check. However, it provides a false sense of security.

**Fix:** Move admin checks to a server-side API endpoint.

---

### S-16. `ml_user` cookie is not HttpOnly — LOW

**File:** `api/line-auth.js:100`

```js
`ml_user=${encodeURIComponent(profile.displayName)}; Path=/; Secure; SameSite=Lax; Max-Age=...`
```

The `ml_user` cookie (display name) is not HttpOnly, making it accessible to JavaScript. This is intentional (client-side display), but the display name is user-controlled data that could contain special characters.

## 2. BUGS & ISSUES TO FIX

### B-01. `verifyToken` crashes on malformed input — HIGH

**Files:** `api/book-key.js:12`, `api/ecpay-create.js:21`, `api/user-books.js:13`

```js
const data = Buffer.from(b64, 'base64').toString();
// ...
const payload = JSON.parse(data);
```

If `b64` contains invalid base64 or the decoded string is not valid JSON, `JSON.parse()` will throw an unhandled exception, crashing the request handler with a 500 error instead of returning a clean 401.

**Fix:** Wrap in try-catch and return null on parse failure.

---

### B-02. `content.js` will crash if `content.json` is missing — MEDIUM

**File:** `api/content.js:5`

```js
const content = JSON.parse(
  fs.readFileSync(path.join(process.cwd(), 'content.json'), 'utf-8')
);
```

No try-catch. If `content.json` is missing or malformed, the entire module fails to load, potentially breaking the Vercel deployment.

**Fix:** Add error handling.

---

### B-03. `briefs.js` does not handle fetch failure — MEDIUM

**File:** `api/briefs.js:6-16`

```js
const r = await fetch(...);
const data = await r.json();
res.json(data);
```

No `try-catch`, no check of `r.ok`. If Supabase is down, this returns an unhandled error.

**Fix:** Add error handling consistent with other endpoints.

---

### B-04. `features.js` does not handle fetch failure — MEDIUM

**File:** `api/features.js:9-16`

Same issue as B-03. No error handling around the fetch calls.

---

### B-05. `brief.js` POST does not handle fetch failure — MEDIUM

**File:** `api/brief.js:30-36`

The POST handler for creating briefs has no try-catch and does not check `r.ok`.

---

### B-06. `site-config.js` POST uses PATCH but does not handle "key not found" — MEDIUM

**File:** `api/site-config.js:33-38`

If the config key does not exist, the PATCH will succeed but update zero rows. The response will be an empty array, which the caller cannot distinguish from success.

**Fix:** Use upsert or check the response for empty results.

The same device-parsing function is copy-pasted in three locations. Changes to one will not propagate.

### B-08. Duplicated `verifyToken()` function across 3 files — LOW

Same token verification logic duplicated. A bug fix in one won't apply to others.

### B-09. `ecpay-callback.js` login log fires without await — LOW

The Supabase insert for logging the login is fire-and-forget (no `await`). This is intentional for performance but means login log failures will be silently lost.

```js
OrderResultURL: `${baseUrl}/app/purchase-result.html`,
```

This page (`/app/purchase-result.html`) does not exist in the `public/` directory. After a customer completes payment, they will see a 404 error.

## 3. FEATURES TO ADD

### F-01. Missing purchase result page — HIGH

Referenced at `api/ecpay-create.js:136` as `/app/purchase-result.html`. Users completing ECPay payment have nowhere to land. This directly impacts payment UX.

---

### F-02. No rate limiting on any API endpoint — MEDIUM

None of the 20+ API endpoints have rate limiting. The most vulnerable:
- `api/scottsu-chat.js` — calls Azure OpenAI (costs money per request)
- `api/scottsu-tts.js` — calls Azure Speech (costs money per request)
- `api/track.js` — writes to Supabase on every call
- `api/inquiry.js` — public POST with no rate limit (spam vector)
- `api/partner-apply.js` — public POST with no rate limit
- `api/mvp-generate.js` — public POST

**Fix:** Add rate limiting via Vercel Edge Middleware or per-endpoint IP tracking.

---

### F-03. No CSRF protection on POST endpoints — MEDIUM

Endpoints like `api/ecpay-create.js`, `api/inquiry.js`, `api/partner-apply.js`, and `api/mvp-generate.js` accept POST requests with no CSRF token validation. Combined with `Access-Control-Allow-Origin: *`, this enables cross-site attacks.

---

### F-04. No input length validation on several endpoints — MEDIUM

- `api/scottsu-chat.js:78` — `message` field has no max length before being sent to Azure OpenAI
- `api/scottsu-tts.js:7` — `text` field has no max length before being sent to Azure Speech
- `api/inquiry.js:16` — `message` has no max length
- `api/mvp-generate.js:18` — `description` has no max length

An attacker can send very large payloads, increasing API costs or causing timeouts.

---

### F-05. ECPay production switch not documented — MEDIUM

**Files:** `api/ecpay-create.js`, `api/ecpay-callback.js`

The ECPay integration uses staging defaults. There is no documentation or checklist for switching to production. The staging merchant ID `3002607` is ECPay's shared test account and should never handle real payments.

---

### F-06. No subscription expiry check or renewal flow — MEDIUM

**File:** `api/ecpay-callback.js:147-168`

The `grantSubscription()` function creates a subscription with a 30-day expiry but there is no cron job, webhook, or check that handles:
- Subscription renewal
- Expired subscription access revocation
- Recurring billing via ECPay

---

### F-07. No logout endpoint — LOW

There is a LINE login flow (`api/line-auth.js`) but no logout endpoint to clear the `ml_auth` and `ml_user` cookies. Users cannot sign out.

---

### F-08. `api/mvp-generate.js` only saves — no AI generation — LOW

The MVP builder endpoint saves the request to Supabase with status `pending` but never calls an AI API to actually generate the MVP plan. The user sees a "pending" state with no resolution path.

## 4. UI/UX ENHANCEMENTS

### U-01. No loading or error states on most pages — MEDIUM

**Files:** `public/daily-brief/index.html`, `public/features/index.html`, `public/storybook/index.html`

### U-02. Missing `<meta name="robots" content="noindex">` on admin pages — MEDIUM

**File:** `public/admin/index.html` — no robots meta tag
**File:** `public/esl/admin.html` — no robots meta tag

The newer `/admin.html` has `noindex`, but the older admin pages are indexable by search engines. The SQL runner and analytics dashboard could appear in Google results.

**Fix:** Add `<meta name="robots" content="noindex, nofollow" />` to all admin pages.

### U-03. Images without alt text — LOW

**Files:**
- `public/admin/index.html:234` — user avatars have no alt text in the dynamically generated `<img>` tags
- `public/dbtc.html:52,128` — avatar images have empty `alt=""`

- `public/ai-innovator.html:51,122` — avatars with empty alt

### U-04. Tailwind CSS loaded from CDN in production — LOW

**Files:** `public/admin.html:8`, `public/more.html:8`

```html
<script src="https://cdn.tailwindcss.com"></script>
```

The Tailwind CDN script is intended for development only. It adds ~300KB of JavaScript and generates styles at runtime, hurting performance.

**Fix:** Use Tailwind CLI to build a production CSS file, or switch these pages to inline styles matching the rest of the site.

---

### U-05. Inconsistent styling across pages — LOW

The codebase uses three different styling approaches:
1. **Inline/custom CSS** — `index.html`, `esl/`, `agents/`, `scottsu/`, `namecard/`, `storybook/`
2. **Tailwind CDN** — `admin.html`, `more.html`, `dbtc.html`, `ai-innovator.html`, `arita/`, `audrey/`
3. **Dark theme** — `admin/index.html`, `esl/admin.html` (custom dark CSS)

No shared CSS variables, design tokens, or component library. Visual language differs significantly between pages.

---

### U-06. No favicon on most sub-pages — LOW

Only `index.html` and `namecard/` define a favicon. All other pages inherit the browser default or nothing.

---

### U-07. No Open Graph / social sharing meta tags on most pages — LOW

Only `index.html` has a `<meta name="description">`. Most pages lack Open Graph tags (`og:title`, `og:description`, `og:image`), which means shared links on LINE, Facebook, etc., will show generic or broken previews.

---

### U-08. Accessibility: no skip navigation, no ARIA landmarks — LOW

None of the pages have:
- Skip-to-content links
- ARIA landmark roles (`main`, `navigation`, `banner`)
- Focus management for modals (agents detail modal, chat modals)
- Keyboard navigation support for interactive elements

---

### U-09. No 404 page configured in Vercel — LOW

**File:** `vercel.json` has no `"cleanUrls"` or `"trailingSlash"` config, and no custom 404 page. Visiting any invalid URL returns Vercel's generic 404. The `member.html` page serves as a manual 404 but only for that specific URL.

**Fix:** Add a `public/404.html` and configure in `vercel.json`.
